## Executive summary

If you run a Node.js service that accepts compressed request bodies, or a Node.js client that fetches compressed responses, this one is yours. CVE-2026-111497 is an out-of-bounds write in the Google Brotli decoder [1], the compression library that Node.js bundles for `node:zlib` [3], and that .NET, Envoy, Istio, Bun, the Python bindings and a long list of other products also carry [2]. A crafted Brotli stream can corrupt the decoder's memory, and the CVE record says that can lead to memory disclosure, denial of service or possibly code execution [1]. The upstream fix, a small change to how one decoder function reports an error, sat on Brotli's default branch (`master`) from February 2026 until security releases shipped on 21 October 2026 [7] [6]. CISA added it to the Known Exploited Vulnerabilities catalog six days later [9].

The researchers who wrote it up call it Node2Shell (**Reported**: Imperva, ELLIO) [16] [17]. This study is lab-backed. On 4 November 2026 a lab host ran two Express 5 containers that differed only in the Node.js runtime, 24.22.0 against 24.22.1, and sent each the same read-only probe from a public scanner [27]. The verdicts differed: the scanner flagged the 24.22.0 target and not the 24.22.1 one, with different responses to the same probe (**Demonstrated**) [27]. The lab also turned up the most useful practical finding in this study: the Brotli version that Node.js reports about itself is `1.2.0` on the vulnerable runtime and on the fixed one. A version check that trusts the Brotli string will flag a fixed Node.js host as vulnerable and will never see the upgrade land (**Inferred** from the lab result and the CVE's 1.0.3 to 1.2.0 range). Only `node --version` tells them apart (**Demonstrated**) [27].

Evidence grade: the vulnerability, the fixed versions and the KEV listing are **Confirmed**; the remote code execution write-ups and the in-the-wild traffic report are **Reported**; the lab's version check, differing probe verdicts and the fixed-runtime result are **Demonstrated**.

### Key findings

- **The bug is a decoder that did not stop.** An invalid block switch was treated as a temporary shortage of input rather than a permanent format error, so the streaming decoder went on filling an eight-byte internal buffer past its end (**Confirmed**: Node.js) [3]. The upstream fix makes the block-switch decoder return a named format error, `BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH`, instead of a bare `false` its callers ignored, which this study reads as the unchecked return value of CWE-252 (**Inferred**) [7] [1].
- **The fix waited eight months for a release.** The fix commit landed on Brotli's default branch (`master`) on 27 February 2026 with no release. It shipped in Brotli 1.2.1 (as cherry-pick `b418fa81`) and in the Node.js security releases on 21 October 2026, and the CVE was published the next day [7] [6] [5] [1].
- **The Brotli version string cannot confirm the Node.js fix.** Node.js 24.22.1 did not bump its bundled Brotli. It cherry-picked the one upstream commit, so `process.versions.brotli` still reads `1.2.0` (**Confirmed**: Node.js release notes [4]; **Demonstrated**: lab [27]).
- **The lab saw a different answer, not a crash.** The same 23,068,764-byte probe drew HTTP 200 from the vulnerable runtime and HTTP 400 with a block-switch decoder error from the fixed one. The vulnerable container stayed up. The lab plan had expected it might crash; it did not (**Demonstrated**) [27].
- **The fix is the runtime, not the middleware.** The lab's Express 5.3.0 resolved body-parser 2.4.0, newer than the 2.0.0 to 2.3.0 range one write-up lists as reachable, and the vulnerable runtime was still flagged (**Inferred** from the lab and the Node.js advisory) [27] [16] [3].
- **CISA says it is being exploited.** CISA lists it as known exploited [9], and ELLIO reports a 23 MB Brotli body aimed at Node 24.22.0 on 26 October 2026 whose final stage failed in ELLIO's own testing (**Reported**) [17].

### Top recommendations

1. Upgrade Node.js to v22.23.4, v24.22.1, v26.12.1 or later, and rebuild every image built `FROM` an older `node` tag. On 4 November 2026 the download page listed v24.22.2 and v26.13.0 as the current LTS releases [3] [18].
2. Check Node.js with `node --version`, never with `process.versions.brotli`. The Brotli string reads `1.2.0` on vulnerable and fixed runtimes alike [27] [4].
3. Inventory the other copies of Brotli: the system `libbrotli`, PyPI `brotli` and `brotlicffi`, Go `andybalholm/brotli`, .NET runtimes and the proxies in front of your services. Each has its own fixed version (Part 5) [2] [8] [11] [14].
4. Treat it as a KEV item with a date. CISA's due date is 10 November 2026 [9]; plan to meet it whether or not your organization is bound by it.
5. Do not count on crash or error logs to catch a successful attack. In the lab, the block-switch decoder error appeared only on the patched host, and the vulnerable host logged no error for the probe (**Demonstrated**, 02-test.txt) [27].

## Part 1: the flaw

### Where it lives

Brotli is a general-purpose lossless compression format, specified in RFC 7932 (**Confirmed**) [28]. HTTP carries it as the registered `br` content coding, which a sender names in the `Content-Encoding` header (**Confirmed**) [29] [30]. Google's reference implementation is a C library, and its decoder lives in `c/dec/decode.c` [1]. Node.js ships that library inside the runtime and exposes it through `node:zlib`, so any Node.js code that decompresses Brotli data, its own or a framework's, runs Google's decoder [3].

A Brotli stream is a header followed by a series of meta-blocks, and inside a meta-block the data can switch between block types. Each block-switch command is a pair of a block type and a block count, and the decoder reads a new pair from the stream when the current count runs out (**Confirmed**: RFC 7932) [28]. The CVE record describes the result: an out-of-bounds write that lets a remote unauthenticated attacker corrupt adjacent decoder state, disclose memory, cause denial of service or potentially execute code with a crafted stream (**Confirmed**: CNA) [1]. The CNA's title is "Out-of-Bounds Write in Google Brotli Decoder" [1].

### The mechanism

Node.js describes it in one sentence (**Confirmed**) [3]. When the decoder met an invalid block switch, it reported a temporary need for more input instead of a permanent format error. A streaming decoder that thinks it needs more input asks for more and keeps appending it, and here it kept appending to an eight-byte internal buffer. That is the out-of-bounds write.

The fix commit shows why it happened (**Confirmed**: Brotli commit `0ed4268`) [7]. The function that decodes the block type and length, `DecodeBlockTypeAndLength`, returned a plain boolean, and its callers did not act on a `false`. The fix changes it to return a decoder error code, `BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH`, so an invalid switch now ends the stream with an error. The commit touches `c/dec/decode.c` and the public header `c/include/brotli/decode.h`, and its subject is "Detect and report invalid stream earlier." [7] [6]. The two weaknesses the CNA lists match the two halves of this: the unchecked return value (CWE-252) is the cause and the out-of-bounds write (CWE-787) is the effect [1] [2] (**Inferred**).

ELLIO dates the bug to Brotli 1.0.3, released in March 2018 (**Reported**) [17]. The Debian security tracker names commit `35e69fc` in v1.0.3 as the change that introduced it [12]. The CVE record's affected range starts at the same release [1].

### How an attacker reaches it

The Node.js advisory's condition is simple: the flaw is reachable when an application decompresses attacker-supplied Brotli data with `node:zlib` (**Confirmed**) [3]. The research write-ups name the common ways that happens (**Reported**: Imperva) [16]:

- **Server side.** Express 5.0.0 to 5.3.0 and body-parser 2.0.0 to 2.3.0 decode `br` request bodies in Brotli-capable parsers such as `json()` and `raw()`. A request to such a route with `Content-Encoding: br` hands the body straight to the decoder.
- **Client side.** Node's built-in `fetch()` decodes `br` responses, so a Node.js client that fetches from an attacker-controlled server is exposed.
- **Not by itself.** A bare `node:http` server does not decode incoming Brotli bodies on its own; the application or a framework has to.

The lab showed that the body-parser range is not the boundary: body-parser 2.4.0 on the vulnerable runtime was still flagged (Part 4). On .NET, the vendor names the same two directions: ASP.NET Core request decompression with `br`, and `HttpClient` automatic decompression that includes Brotli, plus direct use of `BrotliStream` or `BrotliDecoder` (**Confirmed**: .NET advisory) [14].

## Part 3: exploitation

Three kinds of evidence exist, and they carry different weights.

**The listings (Confirmed).** CISA added the CVE to the Known Exploited Vulnerabilities catalog on 27 October 2026 with a due date of 10 November 2026, CWE-252 and CWE-787, and known ransomware campaign use marked Unknown [9] [10]. The catalog's required action is to apply vendor mitigations per BOD 26-04 [10]. Four days earlier, CISA's Vulnrichment SSVC entry in the CVE record had already marked exploitation as active and technical impact as total, with automatable marked no [1]. KEV and SSVC are CISA's judgments; neither names an actor or a victim.

**The research reproductions (Reported).** Imperva's Ron Masas reported remote code execution against the official `node:24.22.0` Linux arm64 image on 22 October; it took multiple attempts, and 24.22.1 rejected the same inputs [16]. ELLIO reports reproducing remote code execution on unmodified official x86-64 Node builds with ASLR on, using an offset specific to each build. It adds that failed attempts crash worker processes, a denial of service in themselves, and that the resulting core dumps may hold secrets [17]. Imperva makes no claim of exploitation in the wild [16]. Neither exploit was examined for this study.

**The traffic (Reported).** ELLIO Threat Research Lab reports a scanner that calls itself `node2shell-check`, from a source in AS44620 that its sensors first saw on 13 June 2026, followed on 26 October 2026 at 15:08 UTC by a 23,069,983-byte Brotli body aimed at Node v24.22.0 on x86-64 [17]. ELLIO says the payload's final stage failed in its own testing [17]. The June date is when that source address first appeared, not evidence that this CVE was being probed in June (**Inferred**).

The honest summary: CISA says it is exploited, two research teams say code execution works on stock builds with effort, and one sensor network saw an attempt whose payload ELLIO could not get to work in its own testing. That is enough to patch on the KEV clock. It is not evidence of a mass-scanning wave of the PHP2Shell kind, which [the PHP2Shell study](/case-studies/PHP2SHELL_OCTOBER_2026.md) covers for the same month.

## Part 4: what the lab showed

The lab ran on a lab host on 4 November 2026 UTC, with every target bound to loopback and every container removed afterwards [27]. The screenshots are renderings of the captured terminal output with a neutral `lab$` prompt and the lab host anonymized. The test step itself, the scanner's probe, is described below and not shown.

### Setup: two targets that differ only in the runtime

Both targets were built from the same Dockerfile and the same two-route Express 5 app, `server.js`, whose body parser is `express.json({ limit: '100mb' })` [27] (01-setup.txt). One image was built `FROM node:24.22.0` (digest `sha256:925de64a...f017f5`) and the other `FROM node:24.22.1` (digest `sha256:d862bb5d...108ea`) (**Demonstrated**, 01-setup.txt). `npm ls` in each container resolved the same tree, `express@5.3.0` with `body-parser@2.4.0` (**Demonstrated**, 01-setup.txt and 03-exposure.txt). Each container published its port on `127.0.0.1` only, and each printed its banner:

```text
LAB-READY node=v24.22.0 brotli=1.2.0
LAB-READY node=v24.22.1 brotli=1.2.0
```

(**Demonstrated**, 01-setup.txt)

The setup did not go as planned, and the capture records it (**Demonstrated**, 01-setup.txt). The first image builds failed: npm stopped with `EAI_AGAIN` and pip with name-resolution errors, because the build containers could not reach the lab's private resolver. The retry resolved the three public registry hosts on the lab host and passed them to the builds with `--add-host`. ### The version check

```text
lab$ docker exec n2s-vuln node --version; docker exec n2s-fixed node --version
v24.22.0
v24.22.1
```

Over HTTP, each app's `/version` route reported its runtime and its bundled Brotli (**Demonstrated**, 02-test.txt):

```text
{"node":"v24.22.0","brotli":"1.2.0"}
{"node":"v24.22.1","brotli":"1.2.0"}
```

This is the study's key finding. The bundled Brotli version is `1.2.0` on the vulnerable runtime and on the fixed one, so the Brotli string cannot confirm the fix; only the Node.js version can (**Demonstrated**, 02-test.txt). ELLIO reports the same for patched and vulnerable builds (**Reported**) [17]. The reason is in the release notes: Node.js 24.22.1 did not move its bundled Brotli to 1.2.1, it cherry-picked commit `0ed4268` into the copy it already had (**Confirmed**) [4]. A plain JSON control body, `{"a":1}`, was accepted by both targets with `keys:1` (**Demonstrated**, 02-test.txt).

### The test step, described

Over loopback, the MIT-licensed Assetnote node2shell-scanner (commit `bf2dc387`, 25 October 2026) sent four one-byte control requests, one 23,068,764-byte Brotli probe with `Expect: 100-continue` and a final one-byte control to `/api/json` on each target, the fixed target first (**Demonstrated**, 02-test.txt, fixed.json, vuln.json). The lab plan classes the scanner as a read-only probe, and no code execution was attempted (plan.json).

### What differed

| Observable | node 24.22.1 (fixed) | node 24.22.0 (vulnerable) | Capture |
|---|---|---|---|
| Scanner verdict | `NOT VULNERABLE`, `NO SIGNAL` | `VULNERABLE` | 02-test.txt, fixed.json, vuln.json |
| Probe response | HTTP 400, `text/html`, 359 bytes (the malformed-Brotli class) | HTTP 200, `application/json`, 38 bytes (the valid-route class) | fixed.json, vuln.json |
| Final control | HTTP 200 | HTTP 200 | fixed.json, vuln.json |
| Last application log entry | `Error: Decompression failed`, code `ERR__ERROR_FORMAT_BLOCK_SWITCH`, errno -17, status 400, from `BrotliDecoder.zlibOnError` | No error for the probe; the last entry is the unsupported-encoding `x` control | 02-test.txt |
| Container state after the probe | `Up` | `Up` | 02-test.txt, 04-mitigation.txt |

(**Demonstrated** throughout.) The fixed runtime treated the probe as a malformed stream and said so with the error code the Node.js fix exposes, `BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH` [4]. The vulnerable runtime accepted the same bytes as if they were a valid body. The log entries were attributed by counting the lines of the two `docker logs --tail 20` outputs (02-test.txt).

### What contradicted the plan, and a write-up

**No crash.** The lab plan inferred that the vulnerable container might exit with code 139 (a segmentation fault) or abort after the probe. It did not. `docker ps -a` showed both `n2s-vuln` and `n2s-fixed` up after the probe and still up about a minute later (**Demonstrated**, 02-test.txt and 04-mitigation.txt). A crash is not a reliable sign that this probe reached a host, and Imperva says crashes and decoder errors are not reliable signs of exploitation on their own (**Reported**) [16].

**The body-parser range is not the boundary.** Imperva lists body-parser 2.0.0 to 2.3.0 as reachable [16]. The lab's body-parser was 2.4.0 and the vulnerable runtime was still flagged. Together with the Node.js advisory's statement that the decoder is the one bundled with Node.js [3], the reading is that the runtime carries the fix, not the body-parser version (**Inferred**) [27].

Debian's LTS advisory recommends upgrading the brotli packages [11]. On Debian-family hosts that is one package update for every program that links the system library; on hosts running the official Node.js binaries or images it changes nothing for Node.js, which bundles its own copy [3] [12] (**Inferred**). Expect both kinds on the same host: the lab host had a system `libbrotli` and a separately installed Node.js (03-exposure.txt).

### If you cannot upgrade today

Node.js lists no workaround (**Confirmed**) [3]. .NET does: remove the `br` provider from ASP.NET Core request decompression and limit `HttpClient` automatic decompression to GZip and Deflate (**Confirmed**: .NET advisory) [14]. For Node.js, the bridges a team might reach for are rejecting or stripping `Content-Encoding: br` on request bodies at the proxy, or turning off body inflation in the parser for routes that do not need it. Neither is vendor-documented for this CVE and neither was tested in the lab (**Inferred**) [27]. Neither covers the client-side `fetch()` path [16]. Treat any of them as a way to buy days before the upgrade, not as the fix.

## Part 6: detection

- **Version inventory is the control that works.** Flag Node.js below the fixed lines by `node --version`, system `libbrotli` below the distribution's fixed package, and the language packages below their fixed versions [2] [8] [11]. The lab showed that the Brotli string will not tell you (**Demonstrated**) [27].
- **The public scanner has a recognizable shape.** In the lab it sent a POST to a JSON route with `Content-Encoding: br`, a `Content-Length` of 23,068,764 and `Expect: 100-continue`, preceded from the same source by one-byte `br` controls and a control with the unsupported encoding `x` (**Demonstrated**, fixed.json and vuln.json). That is the scanner's shape; an exploit need not look like it (**Inferred**). ELLIO's in-the-wild body was a similar size, 23,069,983 bytes (**Reported**) [17].
- **Decoder errors mark probes of patched hosts.** On the patched runtime the probe left a 400 and `ERR__ERROR_FORMAT_BLOCK_SWITCH` in the application log; on the vulnerable runtime it left no error and no crash (**Demonstrated**, 02-test.txt). Alerting on that error finds someone probing hosts you have already fixed, not success against the ones you have not (**Inferred**).
- **Crashes are a weak signal both ways.** ELLIO says failed exploit attempts crash workers [17]; the lab's probe did not crash anything [27]; Imperva says crashes and decoder errors are not reliable signs of exploitation on their own [16]. Where a Node.js worker does crash after a large `br` body, keep the core dump under access control: ELLIO warns it may hold secrets [17].

## Part 7: the vulnerability-management view

- **A bundled library hides behind the product's own version.** Node.js ships Brotli inside the runtime, so a software inventory keyed on the library version sees `1.2.0`, flags fixed runtimes as vulnerable and never records the fix. The same pattern, a library copied into a product rather than linked, is why [Log4Shell](/case-studies/LOG4SHELL.md) defeated inventories built on package names (**Inferred**). For Node.js, the product version is the record that counts [4] [27].
- **One CVE, many patch owners.** The decoder is in the runtime team's Node.js, the platform team's .NET, the network team's Envoy and Istio, the data team's Python and ClickHouse, and the operating-system team's `libbrotli` [2]. Route the ticket per copy, not per CVE (**Inferred**).
- **The scores and the clock agree for once.** A 9.8 base score, a KEV listing with a due date and an SSVC "active" all point the same way [2] [9] [1]. The CNA's `AT:P` and the reachability conditions narrow the emergency to services and clients that decode Brotli from untrusted sources, but finding those takes longer than upgrading the runtime everywhere (**Inferred**).
- **A fix on a branch is not a fix in the field.** The upstream commit sat unreleased for 236 days [7] [6]. Projects that vendor a dependency inherit that dependency's release cadence; watching the upstream security branch, not only its releases, is the earlier signal (**Inferred**).

The library's [CVE Reference](/CVE_REFERENCE.md) had no entry for CVE-2026-111497, Brotli or Node2Shell on 4 November 2026 [26].

## Cross-cutting themes

- **Check the product, not the part.** The Brotli string reads `1.2.0` before and after the Node.js fix, so the version a scanner or an engineer reads off the component can be the wrong one to trust when a vendor cherry-picks a fix instead of bumping the library [4] [27]. The same lesson runs through [Log4Shell](/case-studies/LOG4SHELL.md) and the bundled-dependency cases in [the npm supply-chain study](/case-studies/NPM_SUPPLY_CHAIN_ATTACKS.md) (**Inferred**).
- **A quiet fix is a public fix.** An unreleased commit on a public branch is readable by anyone. The 236 days between the Brotli commit and the release were 236 days in which the fix could be diffed [7] [6] (**Inferred**).
- **Absence of a crash is not absence of a hit.** The vulnerable runtime accepted the probe without an error or a crash, while the patched one logged an error. Logging that looks louder on the fixed host is the opposite of what an alert rule usually assumes (**Demonstrated**, with the reading **Inferred**) [27].
- **Lab plans are hypotheses.** The plan expected that the vulnerable container might crash, and one write-up implied a body-parser version boundary; the run showed neither. A lab that writes down its expectations first is how those corrections reached this study [27] [16].
- **Machine-assisted finding is now in the credits.** The CNA and Node.js credit the report to OpenAI Codex Security, with two named researchers [1] [3]. What the tool did and what the people did is not in the record. The direction matches [the AI Threats 2026 study](/case-studies/AI_THREATS_2026.md) and [the CVE-2026-98432 study](/case-studies/LINUX_TCP_UAF_2026.md) (**Inferred**).

### What is overstated and what is understated

- **Overstated:** "remote code execution on any Node.js server." The flaw is reachable only where an application or framework decodes attacker-supplied Brotli; a bare `node:http` server does not do that on its own, and the CNA's vector carries `AT:P`, which fits that condition (Confirmed [1] [3]; Reported [16]; the link between them Inferred). The two code-execution reports needed multiple attempts or a build-specific offset (Reported [16] [17]).
- **Overstated:** the in-the-wild picture. CISA lists the CVE as known exploited [9], but the one public traffic report describes a single body whose final stage failed in ELLIO's own testing, and no opened record names an actor or a victim (Confirmed [9]; Reported [17]). This is not a mass-exploitation wave of the PHP2Shell kind (Inferred).
- **Understated:** the reach beyond Node.js. The same decoder sits in .NET, Envoy, Istio, Bun, the Python and Go packages, the Debian and Ubuntu system library and the other products NVD lists, each with its own fix and its own owner (Confirmed [2] [8] [11] [14]). The researcher name points at one runtime; the patch work spans many (Inferred).
- **Understated:** the inventory blind spot. The Brotli version string reads `1.2.0` on the vulnerable and the fixed runtime, a body-parser version outside the write-up's range was still flagged, and the patched host logged a decoder error while the vulnerable one logged nothing (Demonstrated [27]). Checks built on the component version, the middleware version or error logs all point the wrong way here (Inferred).
- **Understated:** how long the fix was public. The upstream commit sat on Brotli's default branch for 236 days before a release carried it (Confirmed [7] [6]; Inferred for the arithmetic).
